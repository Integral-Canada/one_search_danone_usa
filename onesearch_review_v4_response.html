Limitations & Points of Attention — Status Update

Partially addressed

1. The GA4 join via SE Ranking URL is the weakest link

The pro-rata distribution logic has been implemented: when multiple keywords share the same SE Ranking landing page URL, conversions are now split proportionally by each keyword's Q1 SEO click share rather than assigned in full to every keyword on that URL. This eliminates the double-counting issue identified in the review. The structural dependency on SE Ranking as a conversion bridge remains — keywords without an SE Ranking URL match still receive no conversion data. The correct long-term fix (direct GSC × GA4 attribution via query-level click share) requires adding webmasters.readonly to the OAuth token scope. This is the next step for this issue.

Outstanding

2. Blank Q4 SEM columns are a recurring operational risk

Not addressed in this sprint. The pipeline continues to rely on a single comparison-mode SQR export to populate both periods simultaneously. The recommended approach — two independent period exports merged in the pipeline — is documented but not yet implemented. This remains an operational risk for any quarter where the comparison period is misconfigured at export time.

Partially addressed

3. SE Ranking threshold at 0.50 is low, with no review safety net

The matching threshold has been raised from 0.50 to 0.60, reducing false positives from short or generic keywords. SE Ranking's CPC and intent label columns remain in the masterlist output; scoping SE Ranking's contribution strictly to the position column (column F) as recommended is not yet implemented. The two-source position fallback (SE Ranking first, GSC average position as fallback) is in place and covered under point 7.

Outstanding

4. No scenario or recommendation layer

Not addressed. The pipeline continues to stop at the data layer. The scenario classification and recommendation logic documented in SKILLSEOSEM.md is mature and consistent across deployments. Extracting it into a reusable module remains the highest-value gap between the pipeline as deployed and its client-facing output.

Implemented

5. No multi-language handling

The hardcoded LANG = EN default has been removed from both the normalization step and the keyword study match output. Language is now a per-client configuration parameter. For any keyword that does not receive a language value from the keyword study match, the client's configured language is applied as a fallback at the merge step. The pipeline is structurally ready for bilingual deployments.

Outstanding

6. No Quality Score (QS) integration

Not yet addressed. The quality report is read as a source input but not written to the masterlist. QS by keyword and QS by landing page are not surfaced as columns. This remains a gap for any client where SEO/SEM overlap drives investment decisions.

Implemented

7. SE Ranking position gaps — two-source fallback logic

Implemented. When column F has no SE Ranking position, the pipeline checks GSC average position for that keyword and writes it rounded to the nearest integer. In the Oikos USA test run, 45 of 52 populated position values came from the GSC fallback — confirming the fallback is doing meaningful work across the full keyword spine, not only for edge cases.

Implemented

8. Multi-brand architecture not supported

The hardcoded single-brand constants have been replaced with a CLIENTS dictionary. Each brand is a named configuration entry holding its own sheet IDs, tab names, and language setting. The pipeline accepts a --brand argument and a --brand all flag to run all configured brands in sequence. Adding a new brand requires only a new entry in CLIENTS — no changes to pipeline logic.

Outstanding

9. The decision layer already exists — in SKILLSEOSEM.md

Not addressed in this sprint. The SKILLSEOSEM.md recommendation engine has not been codified into the pipeline. This is a codification task rather than a data task and is the logical next step once the data layer is fully stable.

Implemented

10. Volume plan vs volume actif — critical distinction absent from the pipeline

The distinction is now documented and surfaced in the pipeline summary log. At the end of each run, the log reports both volC (total planned keyword volume — all rows with an average search volume from the keyword study) and osVolC (volume restricted to keywords that generated at least one SEO click in either period). The Coverage formula in columns J/K correctly uses per-keyword click-to-volume ratio, which aligns with the osVolC basis for trend analysis.

Implemented

11. SQR filtering — Performance Max must be excluded

Implemented. norm_sqr() now drops rows where Campaign Type contains "performance max" and drops aggregate summary rows beginning with "Total:". In the current Oikos USA export, no Performance Max rows are present — campaign types are Generic, Brand, and Conquesting — so the filter has no effect on current data. It is in place for any future export that includes PMax.

Outstanding

12. GA4 event structure varies by client

Not yet addressed. The GA4 ingestion layer continues to assume the Oikos USA event structure (mikmak_checkout, mikmak_click_offline_store). The conversion signal is not configurable from the source config sheet. This requires a configurable event-name or metric-column field in the source config before onboarding any client with a different GA4 export format.

Outstanding

13. hreflang cannibalization — undetected blind spot

Not addressed. The pipeline does not collect a ranked URL per country from SE Ranking and therefore cannot detect hreflang cannibalization signals. Resolving this requires either a per-country URL export from SE Ranking or a dedicated hreflang audit layer external to the current pipeline.

Implemented

14. Connection-intent keywords pollute SEM performance metrics

Implemented. A configurable exclusion list is applied after normalization and before the GSC × SQR merge. Terms such as login, website, my account, mon compte, se connecter, and espace client are excluded from both sources. The list operates on normalized forms and is exact-match only, so it can be extended without risk of unintended partial matches.
