2. **SEM QV attribution methodology can produce QV > SEM clicks — shared code, likely affects Activia too.** Found 2026-10-04 while investigating International Delight's real data (`pipeline/sem_qv.py::calculate_qv_sem()`): QV SEM is computed as an attribution rate pooled across ALL keywords sharing a landing page in the GA4 Ads session export (`LP conversion rate = sum(GA4 key_events)/sum(GA4 sessions)` for that page, then `keyword's share of LP sessions × LP key_events`) — not capped at that keyword's own click count, and sourced from a different system (GA4 sessions) than "SEM clicks" (Google Ads SQR export). This is shared code used by every brand, including Activia — it is a **methodology property, not a bug**, but Activia's dashboard likely has the same QV-can-exceed-clicks pattern on some keywords and that should be disclosed/caveated the same way for Activia's deliverable, not presented as if QV is a simple per-keyword click-capped figure. Not yet checked directly against Activia's real data — just flagging the shared mechanism.

3. **Silent previous-period GA4 skip — shared code, worth verifying Activia's own config.** `run_pipeline.py::read_ga4_both_periods()` silently returns `{}` (just a log line, no hard stop, no flag surfaced to the dashboard) when a brand's previous-period GA4 conversions export isn't registered in the source registry. Confirmed this is exactly why International Delight's Q1 2026 SEO QV is 0/blank for all 2,407 rows (registry never had "...Q1 2026" rows for Checkout/Click-Offline-Store conversions). This is the same class of problem as the already-known [[feedback_gsc_403_hard_stop]] rule (a missing/failed data source should hard-stop or flag, not silently degrade). **Action for Activia:** verify the registry (`16-h0rmI...` → `ACTIVIA USA` tab, or equivalent) actually has previous-period ("...Q1 2026") rows registered for every GA4 conversion source Activia uses — if not, Activia's dashboard likely has the same "everything shows as NEW" problem in its previous-period QV/conversions columns, silently.

4. **SE Ranking volume-gap footnote — IMPLEMENTED in shared code 2026-10-04, not yet applied to Activia's built file.** Per user request ("automatically include an asterisk... to explain it"), `scripts/build_html_oikos.py::build_territory_panel()` now flags any Top-Keywords-table row where OneSearch clicks exceed SE Ranking's indexed volume, or volume is missing entirely despite real clicks, with a red `*` superscript next to the keyword, and appends one explanatory footnote per territory panel (only when at least one row is flagged). This is shared rendering code (`build_territory_panel` is called identically by the direct Oikos path and by every brand's generic `build_html.py`-patched path), so it will apply automatically to Activia, Oikos, Silk, and ID the next time each is rebuilt — **Activia's currently-committed dashboard (`76d261c`) does not have this yet**, since it predates the change. No rebuild has been triggered for any brand as part of this change.

5. **`normalize()` silently strips all non-ASCII characters — shared code, real correctness bug, needs checking against Activia's data.** Found 2026-10-04 investigating Silk's "silk 官网" keyword (13,025 Q2 clicks, drives the single biggest territory-coverage loss on Silk's dashboard, -15.4pp BRAND). `pipeline/normalize.py::normalize()` does `re.sub(r'[^a-z0-9 ]', '', s)` — strips ALL non-Latin-script characters, not just punctuation. Result: every CJK brand-navigational query variant ("silk 官网", "silk官网", etc. — confirmed via live GSC country breakdown to be ~80% China/HK/Taiwan/Singapore/Japan/Korea traffic) normalizes to the identical key as the unrelated, legitimate English query "silk" (~70% USA) — both silently merge into one Masterlist row. Not a query-bucketing nuance like the SE-Ranking volume gaps — this is a real bug that merges two semantically different keywords.
   - **Action for Activia:** this is shared code (`pipeline/normalize.py`), used by every brand's ingestion. Any Activia keyword containing non-ASCII characters (accents, non-Latin scripts, special symbols) that happens to collide with an unrelated ASCII keyword after stripping would silently merge the same way. Not yet checked against Activia's real Masterlist — worth a quick scan for any non-ASCII characters in Activia's real GSC query data before assuming this is Silk-specific.
   - **Not yet fixed anywhere** — proposed fix (strip punctuation/symbols only, preserve letters from any script) needs testing against the fuzzy-matching step that also depends on `normalize()`, then a re-run of affected brands' ingestion. Full detail in `SILK_REVIEW_FINDINGS.md` point 4.
